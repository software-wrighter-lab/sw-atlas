You want a campus-specific docent model that is small enough to download and run entirely in-browser, answers questions about the campus, routes visitors to exhibits, explains what they are looking at, and can be retrained as the campus evolves.

The useful lesson from TypeSafe’s System One/Jev work is not “copy Jev.” It is: constrain the docent’s job much more aggressively than a normal chatbot. Jev is built around unstructured input → typed, probabilistic decisions, with outputs chosen from a known schema rather than unconstrained prose. That is a very good fit for your campus.

2. Make DocentDecision the fundamental output

I would define something approximately like:

struct DocentDecision {
    intent: Intent,
    destination: Option<PlaceId>,
    topic: Option<Topic>,
    confidence: f32,
}

with something like:

enum Intent {
    Navigate,
    Explain,
    Recommend,
    Story,
    Status,
    Clarify,
    Unsupported,
}

You can make it richer later:

struct DocentDecision {
    intent: Intent,

    primary: Option<PlaceId>,
    alternatives: Vec<PlaceId>,

    story: Option<StoryId>,

    confidence: f32,
    ambiguity: f32,
}

Then Rust/Yew owns the behavior.

For:

Where can I try APL?

the model does not generate:

destination  = apl        0.973

Your code constructs the answer using current campus data:

[Take me there]

That means a stale model can't hallucinate a nonexistent URL.

This is almost exactly the software-oriented division TypeSafe is arguing for: use AI where fuzzy interpretation is necessary, then put ordinary deterministic software around it.

3. This makes the browser model much smaller

If you insist that the model itself generate good prose, you are likely looking at something in roughly the 250M–1B parameter class before it starts feeling reasonably conversational.

That can run in current browsers. Transformers.js supports browser inference using WASM or WebGPU, including quantized models, and its 2026 v4 runtime supports newer architectures including MoE and Mamba-family designs.

Hugging Face demonstrates browser inference with things like:

SmolLM2-360M-Instruct
1B-class Llama models
WebGPU
quantized weights
inference in a Web Worker

But I don't think you need that initially.

I would aim dramatically lower:

Docent component	Rough model size
intent classifier	1–10M parameters
destination/concept router	5–30M
combined encoder/router	10–50M
optional generative docent	100–400M
general conversational model	500M–1B+

A 20M parameter INT8 model is only about 20 MB of weights.

At 4-bit:

20M × 4 bits ~= 10 MB

That is an entirely different browser UX from downloading a 500 MB model.

And given how narrow your domain is, I suspect you could go below 20M.

What exactly is being “compressed”?

I'd divide the result of the overnight process into three forms of compression.

First is model compression. The expensive teacher turns lots of ways humans might express the same idea into training examples:

"that little RCA processor"
"the spacecraft CPU"
"COSMAC"
"the old 8 bit RCA chip"
"the processor with sixteen registers"

All collapse semantically toward:

concept: rca-1802

The tiny model learns that mapping. That's genuine statistical compression: thousands of examples become millions of reusable parameters.

Second is knowledge compression. A 10,000-word article does not need to be shipped verbatim if the browser's primary job is discovery. The nightly job can create:

title
date
URL
50-word abstract
concepts
entities
relationships
aliases
embedding
representative questions

Perhaps 2–10 KB describing something that was originally 50 KB.

Third is relationship compression, which may be the most valuable part for your corpus. The expensive process discovers:

blog:engram-revisited
       |
       +-- discusses --> concept:engram
       |
       +-- discusses --> concept:moe
       |
       +-- related --> repo:moe-microscope
       |
       +-- related --> campus:moe-microscope
       |
       +-- related --> blog:serial-parameter-machine

The browser doesn't have to rediscover those relationships.

You spent GPU cycles overnight to discover them once.

That's very much your compress-expensively/decompress-cheaply analogy.

1. Precisely: where are the weights?

There are two sensible formats at different stages.

During training

If we build the model in PyTorch, the canonical training checkpoint should be:

models/
  navigator-v001/
    config.json
    tokenizer.json

    checkpoint/
      model.safetensors       <-- TRAINED WEIGHTS
      optimizer.pt            <-- training only
      trainer-state.json

model.safetensors contains the learned matrices:

token embedding
attention Q/K/V/O
router weights
expert 0 FFN
expert 1 FFN
...
expert N FFN
intent head
concept head

The browser never needs optimizer.pt.

Browser deployment

Export the trained model to:

public/model/
  navigator.onnx             <-- graph + possibly small/shared weights
  navigator.weights.bin      <-- large/external weights
  tokenizer.json
  config.json

ONNX explicitly supports this arrangement. The .onnx graph stores each external tensor's filename, offset and length; ONNX Runtime Web can load the external data file separately.

For your project, however, I would go one step beyond generic ONNX external data:

model/
  core.onnx

  weights/
    shared-q4.bin
    expert-00-q4.bin
    expert-01-q4.bin
    expert-02-q4.bin
    expert-03-q4.bin
    expert-04-q4.bin
    expert-05-q4.bin
    expert-06-q4.bin
    expert-07-q4.bin

knowledge/
  catalog.json
  concepts.bin
  embeddings.bin
  relations.bin

That makes the storage hierarchy visible.

2. What model should you actually build?

I would build this model from scratch, rather than fine-tune Qwen/SmolLM.

But I would not build a generative LLM from scratch.

Build a small encoder MoE classifier/ranker.

My starting configuration would be approximately:

Property	Initial target

Because your desired operation is:

      ↓
semantic representation
      ↓
intent + concepts + ranking

not:

natural language
      ↓

That is the neighborhood I'd target.
